Why five runs before 7 AM ET (and six by 8:05): the day starts at 00:00 ET, operation went 24/7 at 05:00 ET, and that
morning had a live review loop (owner, Muse and the interactive session all active). Then one task (vc8a2c) received a
stream of feedback; each Muse post made it eligible again, and oldest-first ordering always picked it. It took 4 of 6
runs (85% of usage), including one 59-minute run, while the DEPLOY task waited.

"List-price equivalent" is what Claude Code reports per run; the worker runs on the owner's subscription (no API key
or other provider configured on PC2), so it consumes plan usage, not billed dollars.

## Solution (PR #11)
| Change | Why |
|---|---|
| Priority lanes: DEPLOY tasks → this repo's infrastructure tasks → other projects | approved work and the operation itself are never starved by a busy project |
| Inside a lane: never-attempted first, then least recently attempted | fairness between tasks |
| `maxRunsPerTaskPerDay: 2` | one task can use at most a third of the daily budget |
| `runTimeoutMinutes: 60 → 45` | one run holds the single lane for at most 45 min; the instructions require an IN PROGRESS checkpoint before stopping |
| `minFreeMemoryMB: 1500` → `LOW_MEMORY` skip | don't start a run that would fail or slow the owner's apps; retried next tick |
| After each run: stop only processes descended from that run and created after it started | dev/preview servers left by runs were piling up (2 of 9 orphaned PeptideFacts servers were provably the worker's) |
| ~~Daily cap stays 6~~ superseded the same day | see Revision below: no fixed cap |

## Revision: dynamic workload instead of a fixed daily cap (owner, 2026-11-25 ~15:00Z)
Owner directive (chat, quoted for Muse): "I want you both to establish a dynamic workload management system rather than an
arbitrary daily run limit" ... "Do not artificially stop working just because six runs have been completed." ... "Never
enable paid extra usage or switch to paid API access without my approval." Follow-up: "dont worry about the limit and
work if i hit the limit i hit the limit" and "i pay for max so i just want this to work". So: no owner reserve, no pacing.

### What usage information actually exists (checked on PC2)
| Source | What it gives | Used |
|---|---|---|
| `claude -p --output-format stream-json --verbose` | a `rate_limit_event` line per run: `status` (allowed / allowed_warning / rejected), `resetsAt`, `utilization` 0..1 per window (`seven_day`, `five_hour` when near), `overageEnabled`, `isUsingOverage` | yes |
| `--output-format json` (old) | final result only: tokens, list-price cost, turns; no limit data | replaced |
| Env / settings | no ANTHROPIC_API_KEY / auth token / Bedrock / Vertex: no paid API fallback exists | checked |
| Live reading 2026-11-25 14:58Z | weekly 78%, reset 17:00Z; extra usage off at account level (`org_level_disabled`) | evidence |
| claude.ai usage page, ccusage | not readable from a headless run / not installed (nothing installed) | no |

### Behavior now
| Situation | Worker does |
|---|---|
| Work is ready | runs it, back to back (10-min scheduler tick), no daily count |
| Subscription refuses (`rejected`) | `LIMIT_PAUSE` until the reported reset time, then resumes by itself (no extra calls to check) |
| Paid extra usage on or in use | `OVERAGE_GUARD`: no runs (owner approval required to spend it) |
| One task already ran 2x today | goes behind other ready tasks; runs anyway if it is the only one |
| Loop bug | runaway fuse 40 runs/day (`FUSE`) |
| Nothing to do / waiting on Muse | no LLM call (free board pre-check); one idle check a day |

Every skip is recorded as an inactivity period; `usage-summary.json` reports minutes per reason, idle periods of 30 min+,
and the latest usage reading. The daily usage post carries them.
